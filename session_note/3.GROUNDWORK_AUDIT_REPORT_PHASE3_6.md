## 4. Systems Discovery: ASN.1 SAN Concealment & CA-KDC Split-Brain Telemetry

Line-by-line inspection of the live telemetry captured from Windows Server 2019 reveals an undeniable systems vulnerability and telemetry discontinuity that blinds single-host intrusion detection systems:

### 4.1 Discovery 1: ASN.1 SAN Concealment in Windows Event 4887
When generating a CSR with `CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT` enabled, the attacker sets:
- **X.500 Subject:** `CN=khal.drogo` (matching the legitimate requester identity!)
- **ASN.1 Extension `2.5.29.17` (`SubjectAltName`):** `upn=administrator@essos.local`

When the certificate is issued, Windows Security Event 4887 on the Certificate Authority (`SRV03`) logs:
```xml
<EventData>
  <Data Name='RequestId'>21</Data>
  <Data Name='Requester'>ESSOS\khal.drogo</Data>
  <Data Name='Attributes'>ccm:braavos.essos.local</Data>
  <Data Name='Disposition'>3</Data>
  <Data Name='SubjectKeyIdentifier'>18 96 ab 3c c0 e5 aa 92 c2 45 57 ab 72 50 bd 7e 0f ca 2a 49</Data>
  <Data Name='Subject'>CN=khal.drogo</Data>
</EventData>
```

#### Why Single-Host CA SIEM Rules Fail:
Standard SIEM and Sigma detection rules for AD CS inspect `Event ID 4887` by comparing `<Data Name='Requester'>` against `<Data Name='Subject'>`. Because `Requester == Subject` (`ESSOS\khal.drogo == CN=khal.drogo`), **single-host CA rules conclude that the user requested a legitimate certificate for themselves**. The administrative impersonation target (`upn=administrator@essos.local`) is DER-encoded inside the X.509 v3 extension blob, which Windows Server 2019 **does not unpack into the security event XML**.

---

### 4.2 Discovery 2: The CA–KDC Identifier Split-Brain
When the issued certificate is presented to the Domain Controller (`DC03`) for Kerberos PKINIT authentication, the KDC parses the ASN.1 `2.5.29.17` extension, identifies `upn=administrator@essos.local`, and issues a Domain Administrator TGT, logging `Event ID 4768`:

```xml
<EventData>
  <Data Name='TargetUserName'>Administrator</Data>
  <Data Name='TargetDomainName'>ESSOS.LOCAL</Data>
  <Data Name='TargetSid'>S-1-5-21-3304911894-2815406861-4222388662-500</Data>
  <Data Name='ServiceName'>krbtgt</Data>
  <Data Name='PreAuthType'>16</Data>
  <Data Name='CertIssuerName'>CertGraph-Lab-CA</Data>
  <Data Name='CertSerialNumber'>1D0000001048BB8F21B707AABD000000000010</Data>
  <Data Name='CertThumbprint'>997AF7159993D8B08F8196F6674B02D2CE3F9889</Data>
</EventData>
```

#### Why Single-Host KDC SIEM Rules Fail:
The Domain Controller's Security Log sees a valid certificate signed by the enterprise root CA (`CertGraph-Lab-CA`) used to authenticate as `Administrator`. **`Event ID 4768` does not contain the requester identity (`khal.drogo`), the Certificate Template name, or the CA Request ID.** A single-host KDC detector cannot distinguish this attack from a legitimate administrator smartcard logon.

---

### 4.3 Side-by-Side Proof: Resolving the Discontinuity via the CA Database Bridge

The two hosts share disjoint cryptographic schema identifiers:
- **CA Event 4887 (`SRV03`):** Logs `RequestId` (`21`) and `SubjectKeyIdentifier` (`18 96 ab...`). It **omits** `SerialNumber` and `CertThumbprint`.
- **KDC Event 4768 (`DC03`):** Logs `CertSerialNumber` (`1D00...10`) and `CertThumbprint` (`997A...`). It **omits** `RequestId` and `SubjectKeyIdentifier`.

Neither machine's security log can join with the other directly. Our CIPG engine bridges this gap by continuously querying the CA Jet Database (`ICertView2` / `certutil -view -restrict "Disposition=20"`), establishing a unified cryptographic relation:

$$\text{Event 4887} \xrightarrow{\text{SKID: } 18\,96\,ab\dots} \text{CA Database View} \xrightarrow{\text{Serial: } 1D00\dots10} \text{Event 4768 (PKINIT)}$$
